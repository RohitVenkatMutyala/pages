Managing the RAM Stack & Hardware Translation

The "Memory-to-Memory" Stack Model

Our compiler implements a Stack-Based Model targeting the x86-64 System V ABI. It is the exact same strategy GCC uses with Zero Optimization (gcc -O0).

1. The "Fixed-Size" Stack Frame

Whenever a function is called, your code generator executes a standard prologue:

pushq %rbp           # Save caller's base pointer
movq %rsp, %rbp      # Set current base pointer
subq $1024, %rsp     # Allocate 1KB of memory

Instead of calculating exact byte sizes, we pre-allocate a massive, flat block of memory. This guarantees we never accidentally overwrite another function's memory.

2. Variables & The Delivery Trucks

Every variable gets an 8-byte slot as an offset from the Base Pointer (%rbp). Because the CPU cannot add two RAM addresses directly, registers (%rax, %rbx) are used strictly as temporary delivery trucks. They fetch variables from RAM, do the math, drop the result back in RAM, and immediately forget it.

3. Pointers & Memory Addresses

  • Standard Variable: movq grabs the value.
  • Address Of (&x): leaq grabs the Memory Address.
  • Dereference (*p): Grabs the address into a truck, then drives to that coordinate to grab the actual value.

The 16-Byte Stack Alignment Rule

This is a notoriously confusing part of compiler engineering! It trips up almost everyone writing an x86-64 compiler for the first time.

The Hardware Reason

Modern CPUs have ultra-fast hardware called SSE/AVX. Functions in the C Standard Library (like printf or malloc) use these hardware instructions under the hood. The specific assembly instruction they use (movaps) demands that the memory address it accesses is a perfect multiple of 16. If it isn't, the CPU hardware literally panics and throws a Segmentation Fault.

How your stack gets misaligned

Every time you pushq, you move the stack pointer (%rsp) by exactly 8 bytes. If your stack is perfectly aligned at 1024, a single push moves it to 1016 (Misaligned! 1016 / 16 = 63.5). If you call printf right now, it will crash.

The Failsafe: andq $-16, %rsp

Instead of guessing if the stack is aligned, we use a brute-force bitwise mask. $-16 is a giant wall of binary 1s ending in four 0s. Doing a Bitwise AND acts like a cookie-cutter: it keeps the address the same but forces it to round down to the nearest multiple of 16.

To prevent losing our original stack location, we wrap every C-call in this 4-step dance:

movq %rsp, %r15     # 1. Photograph exact %rsp
andq $-16, %rsp     # 2. Round %rsp down to 16
call viz_print      # 3. Call C function (Safe!)
movq %r15, %rsp     # 4. Restore original stack

Why Avoid Register Allocation?

The most highly-optimized compilers (like GCC with -O3) use complex algorithms like Graph Coloring to keep variables inside CPU registers.

However, we explicitly chose not to do this. Here is why:

  • Register Starvation: x86-64 only has ~14 general-purpose registers. If a function has 20 variables, the compiler must write complex code to "spill" variables back to RAM.
  • Algorithmic Complexity: It requires tracking "Live Ranges" to know exactly when a register can be safely overwritten.
