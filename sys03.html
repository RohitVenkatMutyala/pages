sys 03: database scaling

1. The Database Bottleneck

Unlike stateless web servers, you can't just copy and paste a database blindly.

  • If Server A writes data to DB 1, and Server B tries to read it from DB 2, the data is missing! Databases must remain perfectly synchronized, making them the hardest part of any system to scale.

2. Master-Slave Replication

Ideal for: Read-Heavy applications (Twitter, YouTube, Blogs).

Route WRITES to one server, and READS to many servers.

  • The Primary (Master) handles 100% of data creation. It immediately sends a synchronization packet to all Replicas.
  • The Replicas (Slaves) handle 100% of data reading. If you have 10x more readers than writers, you simply add more Replicas.

3. Horizontal Sharding

Ideal for: Massive datasets & Write-Heavy applications (Uber, WhatsApp).

Splitting a giant database into smaller, independent pieces.

  • A router mathematically hashes a User's ID to assign them a permanent database shard. (e.g., Hash % 3).
  • User A's reads AND writes always go to Shard 1. User B's reads AND writes always go to Shard 2. This scales infinitely, but complex queries across multiple shards become very difficult.
