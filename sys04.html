sys 04: distributed caching

1. The Hot Key Problem

Databases are too slow for viral content.

  • Databases (like PostgreSQL or MySQL) read data from Physical Disks. This is slow and consumes heavy CPU resources.
  • If millions of users request the same "Hot Key" (like a trending video ID), the database's Hard Drive queue fills up, causing a catastrophic failure.

2. In-Memory Caches (Redis / Memcached)

RAM is 100x faster than Disk.

  • We spin up a specialized server called a Distributed Cache. It stores simple Key-Value pairs entirely in RAM (Memory).
  • It is lightning fast, but volatile and expensive. We cannot store the whole database here, only the most frequently accessed data.

3. The Cache-Aside Pattern

The App Server acts as the traffic controller.

  • 1. Check Cache: App Server asks Redis. If it's a Hit, return data instantly!
  • 2. On Miss: App Server asks the Database.
  • 3. Write Back: App Server gets data from the DB, saves a copy into the Cache, and returns it to the user. Next time, it will be a Hit!
